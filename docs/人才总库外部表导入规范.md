# 人才总库外部表导入规范

本规范记录已确认的人才总库外部表导入方式。后续同类表格默认沿用，只有新增业务含义、身份无法判定或影响导入安全的问题需要另行确认。用户在当前任务中的明确修正优先于本规范。

## 一、先分析和预览，再导入

- 外部表不要求与系统结构完全一致，先逐表建立“原表字段 → 系统字段 → 处理方式”的映射，再生成导入预览。
- 读取全部工作表，识别真实表头、空行、重复表头、合并单元格和日期分组标题。分组标题不是人员记录，其日期信息可作为来源上下文保留，不推算为联系时间或创建时间。
- 缺少结构化字段、语言含糊或内容暂时不能标准化，不阻止资料明确的人员档案入库；不能对应的业务原文保存到现有 `remarks` 备注字段。
- 人员字段优先保留。无法对齐的字段值以原文字符串存入备注，注明原字段、文件、工作表和行号；错填内容也保留来源，不自动弃用整条人员资料。身份归属冲突的内容注明“归属待核”，不能凭备注留存绕过身份查重或补充到未确认的档案。
- 缺少姓名且无法从原表确认人员身份的行单独列出，不能虚构姓名，也不能随意归到相邻人员。
- 预览必须展示新增、已有档案补充、合并候选及异常记录。长文本、字段冲突和未识别内容不得静默丢弃。
- 用户确认导入、且校验没有阻断问题后继续执行；已在当前会话明确授权的操作不重复请求同一授权。

## 二、已确认的字段处理

| 原表信息 | 系统承接方式 | 处理规则 |
| --- | --- | --- |
| 姓名、姓名变体 | 姓名及其他姓名字段 | 保留真实姓名；合并时保留别名，不由简称虚构全名 |
| 邮箱 | 主邮箱、备用邮箱、其他联系方式 | 同一个人可有多个邮箱，逐个提取、去重和保存；不能据此拆成多个人 |
| 国籍、所在地、简历路径 | 对应现有字段 | 含义明确时直接映射；冲突不擅自选值，原文及来源保留在备注 |
| 来源 | `registration_source` 及备注中的来源记录 | 保留原表实际来源；来源缺失时使用表名标识，不虚构来源渠道 |
| 项目评价＋备注 | `remarks` | 合并保存，分别使用“项目评价：”“备注：”标签，换行分隔；空项跳过，保留原文及换行，不自动换算评分 |
| 单价 | 暂存为备注中的字符串 | 使用“单价：”标签保留完整原文，暂不拆分金额、币种、计价单位，也不统一换算 |
| 联系／测试状态 | 暂存为备注中的原始联系进度 | “已发”“已发测试邮件”表示助理已联系；“已回”表示对方已回复，不代表测试通过 |
| 开拓／联系负责人 | 备注中的负责人信息 | 保留原表负责人，不直接替代系统创建人或操作人 |
| 明确语种、母语 | `resource_language_skill` 与现有语种目录关联 | 处理方式见第三节；不能因为原表称“译员”就自动认定专业能力 |
| 无法明确对应的语言内容 | `remarks` | 人员照常入库，含糊语言保留原文，不强行创建语种或语言对关联 |
| 证书 | 证书字段／记录 | 仅在原表确实提供证书信息时登记；掌握语言不等于取得证书 |

补充说明：

- “是”“已做测试”“已发回”等状态没有进一步业务说明时保留原文，不自动认定通过测试。
- 两个以上邮箱优先保存到现有其他联系方式字段；字段长度不足时使用可容纳的联系方式结构或单独列为待处理项，不截断、不丢失。
- 独立联系方式沿用系统的联系信息权限保护；来源核对文件保存于仓库外，备注不要额外复制已有独立字段承接的邮箱、电话等账号。

## 三、语言简称、多语言与含糊内容

### 明确语言

- 同一单元格可以表示多个语种，必须识别“、”“，”“/”“＋”、换行等分隔形式，逐个匹配、去重；不能只做整个单元格的完全匹配。
- 分割时保留括号语义和英语复合名称，避免把同义名拆成不同语种，或把说明文字误当语言。
- 明确简称可以规范化，例如“阿语 → 阿拉伯语”“西语 → 西班牙语”“葡语 → 葡萄牙语”；只有目录和语义均明确时才建立关联。
- 通用名称优先匹配通用语种。不能因为目录有多个地区变体就遗漏通用语种，也不能把“阿语”强行匹配为“阿拉伯语（现代标准）”。
- 原表明确列出不同语种时分别保存。例如“阿语、纳吉德阿拉伯语”应关联“阿拉伯语”和“纳吉德阿拉伯语”两项，不仅保存到备注。
- 原文清楚而目录确实缺少语种时，可以核对后补充对应目录名称。不得将疑似错字、国家名、泛称或模型猜测直接变成新语种。
- 原表明确母语的按母语登记，明确外语的按外语登记；精通、申请、翻译方向、团队能力等不等同于本人母语。
- 语种目录、个人语言情况、业务语言对和专业能力是不同信息。不得由母语列表自动构造翻译方向，也不得由项目经历或语言对自动认定专业能力。

### 含糊语言：人员入库，原文留备注

- “海地语”“瑞士语”“皮钦语”“蒙古语？”等暂时不能唯一对应、带疑问或缺少具体变体的内容，不强行关联语言目录或语言对表。
- “不确定哪个是母语”“没说”“团队多语言”“所有印度语言”等说明保留原始语义，不猜测具体母语，不把团队能力登记为个人能力。
- 一条内容有明确和不明确两部分时，可关联明确部分；其余原文继续保留在备注，不能丢弃整个单元格，也不能强行解释不明确部分。
- 建议备注格式为“语言待核实（原表母语列）：原文【原表第 X 行】”。原文已经完整保存在备注且可追溯时，不重复追加同一段内容。
- 没有语言可结构化不等于人员未完成入库；验收时必须分别核对人员档案是否存在、原文是否留存、明确语种是否关联。

### 可选的 AI 复核

- 必要时可使用已配置的 `google/gemini-3.8-flash` 协助分析；不可假称已调用，必须记录实际返回模型和完整结果覆盖情况。
- 只发送匿名编号、语言原文、必要语义说明和语种目录，不发送姓名、邮箱、电话等个人资料；返回后在本地关联人员。
- 检查模型是否声称匹配不存在的目录项、相同原文判断是否一致，以及是否将国家名、问号或团队信息误判为本人母语。
- 模型判断和置信度只作核对参考。仍然含糊的内容按本节规则保留备注，不等待其完全解释才让人员入库。

## 四、查重、合并与来源差异

### 人员身份判断

- 邮箱相同只是查重线索，必须结合姓名及其他资料，比较主邮箱、备用邮箱及其他联系方式中的全部邮箱。
- 同邮箱、姓名一致或仅大小写、空白差异，作为同一人合并候选。
- 同邮箱、姓名顺序不同、标点不同、简称与全名等情况，结合其他资料判断，不能只依靠模糊相似度自动合并。
- 同邮箱但姓名明显属于不同人员时，保留独立档案，允许共用邮箱，不因此标记为重复。
- 同名不一定是同一人；没有足够身份依据时保留独立档案。
- “CV中没有提供”“没说”等非邮箱占位文字按缺失信息处理，不能将相同占位文字当作共同邮箱。
- 除表内查重外，必须与目标库已有档案核对；同一人员已存在时补充原档案，不重复新建。

### 合并与补充方式

- 合并预览展示每条原记录的文件、工作表、行号、来源和日期分组，以及不同字段的原值。
- “差异”既包括不同非空值，也包括某行缺失、另一行提供补充的情况；不得仅展示冲突而忽略互补信息。
- 合并后的备注保留各来源及原始差异，不能只留下最终选中的值。相同原文可合并显示，但必须保留涉及的全部行号。
- 已有档案只补空值，保留原有非空业务信息；新旧值不一致时在备注中追加外部来源及差异，不静默覆盖。
- 项目评价、备注、单价、联系进度等来自多行时，都要注明各自来源；不能让后一行覆盖前一行。
- 保存稳定的批次标识／幂等键，重新执行同一批次时不得重复新建人员或重复追加备注。

## 五、执行与验收

- 遵守 `AGENTS.md` 和 `docs/infra.md` 的环境边界。项目运行及数据库操作通过局域网机器的 `E:\xinshi_system\.conda_env\python.exe` 执行，操作前核对主机、目录、Git 提交及实际数据库目标。
- 局域网运行不等于局域网数据库：必须检查实际数据库主机和库名。生产库写入沿用当前任务中已明确的授权范围，本规范本身不构成其他任务的生产写入授权。
- 执行前校验字段类型与长度、语种有效性、身份匹配和文件／计划散列。不得为绕过校验而截断文本或覆盖已有值。
- 仓库外保存导入前备份、审核计划、原始来源和结果报告，不在仓库中提交个人资料或凭据。
- 使用事务和幂等控制；写入前重新核对目标人员，发现并发修改或身份匹配变化时停止该次写入，不能按过期预览覆盖数据。
- 验收新增数量、补充数量、人员编号、每条原记录的去向、来源与差异、所有邮箱、备注原文、明确多语种关联，以及已有业务信息未被意外改变。
- 写入成功后用新事务再次核对实际已提交的数据。报告必须区分已新增、已补充、已在备注保留、缺少身份暂不入库和仍需核实的内容。
- 校验和补充操作优先复用已有记录；已满足规则的内容只核验，不为了表示“处理过”而制造重复写入。
