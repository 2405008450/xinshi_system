# 沟通主题分类与开拓事项

## 使用方式

- 沟通大屏左侧提供两级主题菜单；聊天输入区的“讨论主题”菜单提供相同入口。
- 在标注模块，“标注项目”优先显示；在资源管理模块，“资源开拓讨论”优先显示。调整模块显示顺序不会改变团队排序或当前发送主题。
- 输入区“讨论主题（可选）”标记下一条消息，发送成功后清空，失败时保留。查看某个主题不会自动选择发送主题。
- 已发送的普通消息可通过“分类”设置、更改或清除主题。每条消息只有一个主题路径；一级检索包含对应二级主题。
- 默认检索当前会话；大屏可切换“全部可访问会话”。关键词停止输入 400ms 查询，清空立即查询，结果可定位原消息。
- “安排类、执行类、问题类、想法类”是独立的事项类别。消息菜单可收录已有消息，主题菜单或开拓问题列表也可手工新增事项。
- 收录时保存正文、来源、提出人和主题名称快照。之后修改消息主题不会同步改写已收录事项；后续安排仍需由用户明确添加。
- 手工新增事项的提出人由后端记录为当前用户，来源为“手工新增”，没有虚构的聊天消息或会话。

## 权限与历史数据

- `chat_topics:manage`：维护团队菜单，支持新增、改名、排序、停用和重新启用。
- `chat_topics:classify`：整理本人有权访问的其他人消息；没有该权限时只能分类本人消息。
- 两个权限分别配置，不互相包含。系统超级管理员按既有权限规则获取能力；私聊仍仅双方可访问。
- 收录和手工新增沿用开拓收录权限；开拓事项继续使用原有逐记录可见性、编辑、删除和执行人权限。
- 菜单最多两级，同一父级下名称不区分大小写且不能重复；内置标注项目入口不可改名或停用。
- 停用菜单保留历史关联，不能再用于新分类。历史消息不自动分类。
- 分类清除后保留修订号；菜单、消息分类、事项编辑均使用版本保护，避免覆盖其他人的修改。新增审计和接口时间统一为 UTC+8。

## 接口

| 接口 | 功能 |
| --- | --- |
| `GET /chat/topics` | 团队菜单、迁移就绪状态和当前用户能力 |
| `POST /chat/topics`、`PUT /chat/topics/{id}` | 新增和维护菜单，更新携带 `revision` |
| `GET /chat/topics/messages/{id}` | 获取授权消息的当前分类与版本 |
| `PUT /chat/topics/messages/{id}` | 设置/清除分类，携带 `topic_id` 和 `revision` |
| `GET /chat/topics/search` | 按主题、当前/全部会话、关键词和 `before` 序号检索 |
| 既有三种聊天发送与历史接口 | 增加可选 `topic_id`，发送和分类写入同一事务 |
| `POST /resource-development/issues` | 聊天收录或手工新增；后者携带 `client_request_id` 防止重复请求 |
| 既有开拓问题列表/编辑接口 | 支持主题展示、筛选及独立维护 |

检索在 SQL 层先按当前会话访问权限过滤，再统计和分页。跨会话检索结果不更新任何会话阅读位置。

## 迁移和验收

按既有聊天及开拓问题迁移完成后，追加 `data/migrations/20261012_chat_topics.sql`。迁移创建主题、消息关联与审计表，初始化内置菜单，并允许开拓问题手工来源；不重写历史消息。重复执行保留已维护的菜单、分类和事项。

迁移未完成时主题入口隐藏，普通聊天仍可使用；开拓问题就绪检查避免访问缺失列。常驻服务不自动执行迁移。正式数据库迁移和发布须遵循 `AGENTS.md` 与 `docs/infra.md` 的环境和授权边界。

本机使用项目虚拟环境运行隔离回归：

```powershell
& E:\xinshi_system\.venv\Scripts\python.exe tools/verify_resource_issues.py --backend-only
npm.cmd --prefix frontend test
npm.cmd --prefix frontend run build
& E:\xinshi_system\.venv\Scripts\python.exe tools/verify_resource_issues.py --topics-ui
```

验收脚本核对主机、目录和解释器，创建临时 PostgreSQL 专用实例及服务端口，结束后停止实例；不会连接日常业务数据库。主题浏览器结果保存在 `.tmp/chat-topics-qa/chat-topics-ui-result.json`。
