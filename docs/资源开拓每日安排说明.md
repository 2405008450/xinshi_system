# 资源开拓每日安排

每日安排将每日分工和招聘方向合并，按日期统筹各招聘平台账号的负责人、多个语种或方言、岗位目标及完成检查。一个账号每天一位负责人，多个目标共享一个完成状态。它独立于开拓日志、个人工时、打卡截图和日报，不会修改这些功能的统计来源。

## 使用方式

进入资源开拓，切换到“每日安排”。默认查询香港时区的当天，可选择单日或日期范围查看历史。日期范围只展示已保存的安排；单日无记录时显示“尚未保存”，查询本身不生成记录。

统筹人员选择日期后点击“新增／编辑安排”，可以分配负责人、选择开拓方向、填写岗位目标、关联项目并填写账号及每日备注。每个日期、每个平台账号只保存一份安排；未分配负责人也可以保存，但不能标记完成。BOSS 1、BOSS 2、智联招聘1等分别作为独立账号，不按平台品牌合并。

主表按日期为行、账号为列，只展示负责人、方向标签、岗位标签和完成勾选。右侧独立“详情”列通过左向 Popover 展示当日全部账号的长备注、关联项目、完成操作人及中文日期时间，内容在小窗内滚动；“操作”列单独固定。

岗位目标是可创建的多选文本标签，例如 HR、客服、译员。岗位与语种不强制配对，支持纯岗位目标或纯语种目标；最多100项，每项最多100字符，自动去除首尾空格、空项和重复项。已有“内部招聘”方向保留，不自动转换为岗位标签。

每日安排既有 `timestamp without time zone` 字段采用 UTC+8 本地时间，新增写入与资源开拓审计时钟显式使用 UTC+8，安排响应及审计快照携带 `+08:00`。前端复用公共业务时间格式化，兼容本模块已确认的旧无时区值；不修改存量时间、不做统一加八小时处理。

账号年付情况、赠送额度及使用规则在共享配置的“平台情况说明”中维护，安排编辑只读展示，可选中复制。本次不计算额度用量或余量，也不增加截图上传流程；后续打卡截图应关联每日安排账号单元格 ID，独立记录上传人和时间，不复用个人工时截图。

新日期可点击“沿用最近一次安排”。系统选取目标日期之前最近一次保存的安排，包括跨周末的情况，生成可修改的草稿。只有点击“保存”才创建新日期记录。已有安排不能被沿用操作覆盖。负责人、方向、项目和备注可以沿用，完成状态、操作人和完成时间重新记录。停用人员、失效开拓方向以及不存在的手动关联项目会被跳过，并显示具体提示。

开拓方向支持多选：

- **已发送需求**：显示语种、需求及准确来源项目；标注子订单关联子订单自身。相同语种的不同需求分别保留来源。
- **自选语种／方言**：从已有启用的共享目录选择；新增语种继续使用“平台与选项”的目录维护能力。
- **内部招聘**：作为独立开拓方向，可与语种方向同时选择。

选择需求后自动显示对应项目。手动关联项目支持按项目类型、订单号、项目名称搜索。点击项目可查看详情小窗；详情和进入项目的链接受原有项目权限控制。

需求候选实时读取 `demand_status=confirmed` 且请求未取消的需求。草稿不出现在候选中。取消需求后，只撤回该需求的候选；其他同语种需求及自选语种保留。已保存的安排保留名称和项目快照，并提示“需求已取消”“需求语种已调整”或其他失效原因。已有失效项可保留或手动移除，新选择的需求必须仍然有效。

勾选“已完成”代表当天安排已执行，不要求额度耗尽，也不以招到人为条件。服务端记录实际操作人和完成时间。取消勾选清空当前完成信息，审计记录保留。修改负责人、开拓方向、岗位目标或关联项目会恢复为未完成；只修改备注或调整岗位标签顺序不改变完成状态。沿用时复制岗位标签，但不复制完成信息。

“增加平台”复用共享平台配置，新平台保存后立即增加表格列。编辑窗口支持拖动、位置复位、字段搜索和中间内容滚动，底部保存及取消按钮固定可见。

## 权限和并发

管理员及现有资源开拓代录权限人员可统筹整日安排、分配负责人、沿用及修改每日备注。普通写入人员仅能维护本人已被分配的账号，不能转交负责人。只读人员可查看安排。

保存只合并本次提交的账号单元格，其他账号保持不变。保存及完成检查必须携带每日修订号；若其他人先完成修改，返回 HTTP 409。编辑窗口保留当前草稿，用户可复制需要保留的内容或重新加载后编辑。完成操作人的身份、时间及历史名称快照由后端生成，不能由客户端填写。

## 接口

所有接口位于 `/resource-development`：

| 方法和路径 | 内容 |
| --- | --- |
| `GET /arrangements` | 日期范围分页，返回 `items` 和 `total` |
| `GET /arrangements/{date}` | 单日数据或不落库的空结构 |
| `GET /arrangements/{date}/carry-preview` | 不落库的沿用草稿、来源日期及跳过提示 |
| `PUT /arrangements/{date}` | `revision`、变更的 `cells`，可选每日 `remarks` 和 `carried_from` |
| `PATCH /arrangements/{date}/cells/{platform_id}/completion` | `revision` 及 `completed` |
| `GET /arrangement-options` | 有效需求方向；传 `source_type`、`keyword` 可搜索手动关联项目 |
| `GET /arrangement-project-detail` | 受项目权限控制的基本详情及需求状态 |

账号写入字段为 `platform_id`、可空的 `owner_id`、`targets`、`role_tags`、手动关联 `projects`、`remarks`。`role_tags` 是岗位字符串数组；旧客户端不提交此字段时保留已有岗位，显式提交 `[]` 才清空，新记录默认 `[]`。方向类型为 `request`、`manual`、`internal`；需求来源使用 `request_id` 和 `language_id`，自选仅使用 `language_id`，内部招聘不填写来源 ID。客户端不得提交名称快照或完成操作信息。

## 本机隔离验证和迁移

开发、构建和验收在 PC 的 `E:\xinshi_system` 执行。运行以下命令前，按 `docs/infra.md` 核对主机名、项目目录、Git 提交与数据库目标；所有 Python 命令使用项目 `.venv`。

默认业务数据库可能指向云端。必须核对数据库目标；以下隔离验收脚本会创建只监听 `127.0.0.1` 的临时 PostgreSQL，覆盖 `DATABASE_URL`，并在结束时停止临时数据库。它不会修改默认业务库。

隔离本机数据库迁移入口如下，默认模式仅允许 PC、项目目录及本机数据库目标；同时应用每日安排基础迁移与 `20261009_resource_arrangement_roles.sql` 增量迁移，后者为历史记录添加默认空岗位数组，两者均可重复执行：

```powershell
& '.\.venv\Scripts\python.exe' tools/apply_resource_arrangements_migration.py
```

当前日常服务目标为 `43.132.156.72:15432/xinshi_system`，连接配置本身不授权结构迁移。生产迁移、发布及重启需要明确指令、备份和发布前核查。常驻服务关闭 `LOCAL_SCHEMA_MIGRATIONS_ENABLED`，不得在启动时自动迁移。

获得业务库迁移授权后，可使用下列显式模式。脚本核对精确数据库目标、PC、项目目录及当前提交，仅执行岗位增量迁移，不创建基础表。在同一事务中锁定相关两张表，将结构及完整行内容备份到仓库外并校验 SHA-256，迁移后核对字段约束和原有业务内容。备份目录只授予当前执行用户及 SYSTEM 访问权限。重复执行保留已有岗位内容。

```powershell
$arrangementMigrationCommit = git rev-parse HEAD
& '.\.venv\Scripts\python.exe' tools/apply_resource_arrangements_migration.py `
  --confirm-business-target '43.132.156.72:15432/xinshi_system' `
  --expected-commit $arrangementMigrationCommit
```

获准启动或重启本机服务时，先执行 `deploy/start_local.ps1 -CheckOnly`，再使用统一启动入口；核对桌面会话、实际 UNC 目录、监听进程会话和健康状态。非桌面上下文须按 `docs/infra.md` 检查交互式计划任务，不能回退到 Session 0。
