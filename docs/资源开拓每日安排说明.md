# 资源开拓每日安排

每日安排用于按日期统筹各开拓平台账号的负责人、语种或方言、关联项目及完成检查。它独立于开拓日志、个人工时、打卡截图和日报，不会修改这些功能的统计来源。

## 使用方式

进入资源开拓，切换到“每日安排”。默认查询香港时区的当天，可选择单日或日期范围查看历史。日期范围只展示已保存的安排；单日无记录时显示“尚未保存”，查询本身不生成记录。

统筹人员选择日期后点击“新增／编辑安排”，可以分配负责人、选择开拓方向、关联项目并填写账号及每日备注。每个日期、每个平台账号只保存一份安排；未分配负责人也可以保存，但不能标记完成。

新日期可点击“沿用最近一次安排”。系统选取目标日期之前最近一次保存的安排，包括跨周末的情况，生成可修改的草稿。只有点击“保存”才创建新日期记录。已有安排不能被沿用操作覆盖。负责人、方向、项目和备注可以沿用，完成状态、操作人和完成时间重新记录。停用人员、失效开拓方向以及不存在的手动关联项目会被跳过，并显示具体提示。

开拓方向支持多选：

- **已发送需求**：显示语种、需求及准确来源项目；标注子订单关联子订单自身。相同语种的不同需求分别保留来源。
- **自选语种／方言**：从已有启用的共享目录选择；新增语种继续使用“平台与选项”的目录维护能力。
- **内部招聘**：作为独立开拓方向，可与语种方向同时选择。

选择需求后自动显示对应项目。手动关联项目支持按项目类型、订单号、项目名称搜索。点击项目可查看详情小窗；详情和进入项目的链接受原有项目权限控制。

需求候选实时读取 `demand_status=confirmed` 且请求未取消的需求。草稿不出现在候选中。取消需求后，只撤回该需求的候选；其他同语种需求及自选语种保留。已保存的安排保留名称和项目快照，并提示“需求已取消”“需求语种已调整”或其他失效原因。已有失效项可保留或手动移除，新选择的需求必须仍然有效。

勾选“已完成”时，服务端记录实际操作人和完成时间。取消勾选清空当前完成信息，审计记录保留。修改负责人、开拓方向或关联项目会恢复为未完成；只修改备注不改变完成状态。

“增加平台”复用共享平台配置，新平台保存后立即增加表格列。编辑窗口支持拖动、位置复位、字段搜索和中间内容滚动，底部保存及取消按钮固定可见。

## 权限和并发

管理员及现有资源开拓代录权限人员可统筹整日安排、分配负责人、沿用及修改每日备注。普通写入人员仅能维护本人已被分配的账号，不能转交负责人。只读人员可查看安排。

保存只合并本次提交的账号单元格，其他账号保持不变。保存及完成检查必须携带每日修订号；若其他人先完成修改，返回 HTTP 409。编辑窗口保留当前草稿，用户可复制需要保留的内容或重新加载后编辑。完成操作人的身份、时间及历史名称快照由后端生成，不能由客户端填写。

## 接口

所有接口位于 `/resource-development`：

| 方法和路径 | 内容 |
| --- | --- |
| `GET /arrangements` | 日期范围分页，返回 `items` 和 `total` |
| `GET /arrangements/{date}` | 单日数据或不落库的空结构 |
| `GET /arrangements/{date}/carry-preview` | 不落库的沿用草稿、来源日期及跳过提示 |
| `PUT /arrangements/{date}` | `revision`、变更的 `cells`，可选每日 `remarks` 和 `carried_from` |
| `PATCH /arrangements/{date}/cells/{platform_id}/completion` | `revision` 及 `completed` |
| `GET /arrangement-options` | 有效需求方向；传 `source_type`、`keyword` 可搜索手动关联项目 |
| `GET /arrangement-project-detail` | 受项目权限控制的基本详情及需求状态 |

账号写入字段为 `platform_id`、可空的 `owner_id`、`targets`、手动关联 `projects`、`remarks`。方向类型为 `request`、`manual`、`internal`；需求来源使用 `request_id` 和 `language_id`，自选仅使用 `language_id`，内部招聘不填写来源 ID。客户端不得提交名称快照或完成操作信息。

## 局域网验证和迁移

源码编辑在开发机执行。运行以下命令前，按 `docs/infra.md` 核对调试机主机名、`E:\xinshi_system` 目录和 Git 提交。

默认业务数据库可能指向云端。必须核对数据库目标；以下隔离验收脚本会创建只监听 `127.0.0.1` 的临时 PostgreSQL，覆盖 `DATABASE_URL`，并在结束时停止临时数据库。它不会修改默认业务库。

```powershell
& '.\.conda_env\python.exe' tools/verify_resource_arrangements.py
Set-Location frontend
node --test tests/resourceArrangements.test.mjs tests/resourceDevelopment.test.mjs tests/resourceFriendGrid.test.mjs tests/resourceRequestDailyNotes.test.mjs
node node_modules/vite/bin/vite.js build --outDir ../.tmp/resource-arrangements-dist
node tools/check-build-budget.mjs --dist-dir ../.tmp/resource-arrangements-dist
Set-Location ..
& '.\.conda_env\python.exe' tools/verify_resource_arrangements_ui.py
```

后端验收执行首次迁移和重复迁移，并测试业务、HTTP 权限及相关功能回归。浏览器验收使用隔离构建及可控接口状态，覆盖草稿、关联、失效、冲突、权限和弹窗交互；不向默认业务库写入验收数据。日志和截图保存在 `.tmp/resource-arrangements-*`。

实际迁移入口如下，脚本仅允许局域网主机、项目目录及局域网数据库目标：

```powershell
& '.\.conda_env\python.exe' tools/apply_resource_arrangements_migration.py
```

生产数据库发布需要明确发布指令、备份和发布前核查。若局域网默认业务库仍指向生产，则只完成隔离验收，不对实际业务库执行迁移，也不发布依赖新表的静态页面。

需要重启实际本机后端时，按 `docs/infra.md` 在已登录桌面会话执行；重启后核对 8000 端口进程与 explorer 的 SessionId，并在同一交互式上下文中只读验证实际 UNC 目录。非桌面上下文须检查并使用本机 `XinshiDebugBackendInteractive`，不能回退到 Session 0。
