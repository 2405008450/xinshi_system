# 项目时间与日志时区规范

本项目所有业务记录、时间标记、日志和展示统一以 **UTC+8（香港时间）** 为标准。后续 agent 新增或更新涉及时间的代码时，必须沿用本规范，同时检查所修改功能的时间生成、入库、接口、页面与导出链路，不得依赖运行机器或浏览器的默认时区。

本规范自 2026-10-09 起作为开发约定。历史模块仍需在后续修改时逐项核查；制定规范不代表已有记录已完成时区修复，也不授权生产部署、数据库迁移或维护性数据修改。

## 适用范围

- 业务记录的创建、更新、编辑、上传、删除、审批、分配、交接、跟进、发送、读取等时间。
- 操作历史、审计记录、状态流转、项目进度、聊天记录、通知及“最近由某人编辑于”等时间标记。
- 应用与任务日志、异常日志、导入导出记录、备份及验收报告中的时间和日志文件名中的时间标记。
- 日期筛选、按日统计、日报归属、截止时间、定时任务及跨日判断。
- 本机、旧服务器与云端运行环境中的上述功能。

## 时间语义与统一格式

| 场景 | 统一约定 | 示例 |
| --- | --- | --- |
| 接口与结构化日志的日期时间 | ISO 8601，明确携带 `+08:00`；保留业务所需精度 | `2026-10-09T17:18:43.787825+08:00` |
| 面向用户的业务日期时间 | 按 UTC+8 格式化，沿用模块统一样式 | `2026年10月09日 17:18:43` 或 `2026/10/09 17:18:43` |
| 普通文本日志 | 日期、时间及 `+08:00` 一起输出 | `2026-10-09 17:18:43.787+08:00` |
| 纯日期 | UTC+8 下的业务日期，无时间与时区后缀 | `2026-10-09` |
| 日志、备份文件名的时间部分 | 使用 UTC+8，并注明偏移；遵守 Windows 文件名限制 | `20261009-171843+0800` |

业务时钟优先使用明确的 `timezone(timedelta(hours=8))`。现有明确使用 `Asia/Shanghai` 或 `Asia/Hong_Kong` 的现代业务时间逻辑可以沿用；前端格式化必须显式指定这些时区之一，不使用浏览器默认值。需要严格固定偏移或处理历史日期时，使用固定 UTC+8 偏移，不能假定地域时区的所有历史日期都没有夏令时。

Unix 时间戳、JWT 的 `iat`/`exp`、HTTP 日期及外部协议要求的 UTC 时间保留其协议语义；在进入业务记录、日志展示或报表时统一转换为 UTC+8。时间戳数值本身不加减八小时；耗时和超时计算使用时间差或单调时钟，不以本地时间字符串计算。

## 后端生成与数据库存储

### 时间生成

Python 业务代码必须显式指定时区，不得使用裸 `datetime.now()`、`datetime.today()`、`date.today()` 或无时区的 `datetime.utcnow()` 生成业务时间。纯业务日期从 UTC+8 的当前时间提取。

```python
from datetime import datetime, timedelta, timezone

BUSINESS_TIMEZONE = timezone(timedelta(hours=8))

now = datetime.now(BUSINESS_TIMEZONE)
business_date = now.date()
```

优先复用当前模块或项目已有的公共时间能力。多个模块需要同类能力时应抽取公共工具，不在页面、路由和服务中长期复制时间换算代码。

### 带时区字段

新增需要表示实际发生时刻的字段优先使用 SQLAlchemy `DateTime(timezone=True)`，写入带时区的时间。PostgreSQL `timestamptz` 保存的是实际时刻，其内部存储不等于保存原始 `+08:00` 文本；读取与序列化时仍须按 UTC+8 转换。

已有带时区值使用 `astimezone(BUSINESS_TIMEZONE)` 转换。不得对已有 UTC 或其他时区值直接调用 `replace(tzinfo=BUSINESS_TIMEZONE)`，这种写法会改变实际时刻。

### 现有无时区字段

修改旧模块前，先确认 `DateTime` / `timestamp without time zone` 字段的既有业务语义和历史写入来源。已经确认按 UTC+8 保存的字段，继续保存 UTC+8 的本地时间：

```python
# 仅适用于已确认采用 UTC+8 本地时间的无时区字段。
stored_time = datetime.now(BUSINESS_TIMEZONE).replace(tzinfo=None)

# 读取同一字段时补充其已确认的时区，再交给接口序列化。
api_time = stored_time.replace(tzinfo=BUSINESS_TIMEZONE)
```

已经确认历史无时区值实际为 UTC 的字段，应先补充 UTC，再转换到 UTC+8。不得仅根据字段没有时区就把它认定为 UTC，也不得将已经是香港时间的值再次加八小时。

数据库连接目前在 `database.py` 中设置 `timezone=Asia/Hong_Kong`。该设置用于数据库会话，不能替代 Python 业务代码显式指定时区，也不能自动修复无时区字段。数据库默认值、触发器和原生 SQL 生成时间时同样必须遵守字段语义，避免混入服务器系统时间。

## 接口传输与并发版本

- 新增或修改的业务日期时间响应统一转换为带 `+08:00` 的 ISO 8601 值，禁止返回未经说明的无时区日期时间。
- 接收带 `Z` 或其他偏移的输入时，先解析实际时刻，再转换为 UTC+8；输入无时区时间时，必须按字段约定解析，不能使用服务器默认时区。
- 如果兼容旧接口必须暂时保留无时区值，应在模块文档中注明来源时区、兼容范围和后续处理方式。
- `expected_updated_at` 等乐观锁版本必须保留原始精度。页面格式化文本只用于显示，不回传为版本值；时间序列化变化后必须验证旧版本仍被拒绝、当前版本可以正常保存。
- 比较带时区和无时区版本前，应按该字段的存储语义统一转换，不得仅删除未知偏移来比较；协议专用时间不得因业务格式调整而改变实际时刻。

## 前端展示与日期查询

- 所有业务日期时间显式按 UTC+8 展示，不依赖 `new Date(value)` 或 `toLocaleString()` 的默认本地时区。
- 公司管理和共用文档页面目前使用 `frontend/src/utils/dateTime.js` 的 `formatBusinessDateTime`，它将带时区值转换为 UTC+8，并把历史无时区值按业务本地时间解析。使用前必须确认字段符合这一约定；该函数不能自动识别历史 UTC 值。
- 现有 `formatDateTimeMinute`、`formatTimeMinute` 等函数仍依赖浏览器本地时区，不应直接作为新增 UTC+8 展示的实现。修改调用模块时应接入符合本规范的公共格式化能力，并保持该模块原有分钟或秒级展示精度。
- 纯日期不通过 `new Date('YYYY-MM-DD')` 转换时区，防止生日、业务日期、日报日期等发生日期偏移。
- 日期范围按 UTC+8 的零点计算；查询某一天使用“当天零点包含、次日零点不包含”的范围，避免遗漏小数秒记录。列表、总数、导出与统计必须复用同一范围。
- 定时任务的业务触发时间明确使用 UTC+8；按日分组、日报归属和截止日期都基于 UTC+8 日期。时长或间隔计算保持实际时间差语义。

## 日志与导出

- 应用自行生成的日志时间必须显式转换为 UTC+8，并输出 `+08:00`。Python 日志不能只依赖默认 `%(asctime)s`，Node.js 日志不能直接把 `toISOString()` 的 UTC 文本当作业务本地时间。
- 第三方日志需要保留原始证据时，不改写原始内容；在项目日志查看、聚合或导出时提供转换后的 UTC+8 时间，并保留原时区，避免丢失来源信息。
- CSV、Excel、Word、PDF、审计报告及邮件正文中的业务时间均按 UTC+8 输出。文件或列说明中应注明时区；无时区的 Excel 日期单元格写入香港时间，不交由接收端自行推断。
- 同一事件在页面、接口、日志和导出中应对应同一实际时刻，显示精度可以按业务场景不同。

## 历史记录处理

历史时间没有偏移或来源混用时，不得批量加八小时，也不得批量补上 `+08:00` 并宣称已纠正。先核查写入代码、运行环境、日志及用户确认的实际时刻，形成可核对的记录清单，列出来源时区、原值、目标值和判断依据。

历史数据修复与字段迁移需按 `docs/infra.md` 和根目录 `AGENTS.md` 执行，保留备份、回滚方式及审计说明，并取得所需的明确数据维护授权。仅靠未来的规范不能推断或修改存量数据。

## 后续 agent 开发与验收

1. 修改任何包含时间的模块前，阅读本规范，确认字段是实际时刻、纯日期、纯时间还是时长，以及数据库类型和历史来源。
2. 同时检查时间生成、数据库默认值、接口序列化、页面格式化、查询边界、日志和导出，修复所修改功能中依赖服务器或浏览器默认时区的代码。
3. 验证 `2026-10-09T09:18:43Z` 和 `2026-10-09T17:18:43+08:00` 对应同一业务时间 `2026/10/09 17:18:43`，且不会重复加八小时。
4. 验证 UTC 服务器与 UTC+8 服务器生成的业务时间一致；浏览器设置为 UTC、美国西海岸和香港时间时，展示的业务时间一致。
5. 验证跨日、午夜、小数秒、空值、无效值、日期筛选与导出；涉及版本字段时验证乐观锁，涉及定时任务时验证 UTC+8 触发时间。
6. 前端改动执行相关回归和构建，需要展示验证时在实际页面检查；数据库测试使用隔离库。可复用 `frontend/tests/businessDateTime.test.mjs`、`tests/test_company_management_time.py` 和 `tools/verify_company_management_time_ui.py` 中的案例。
7. 交付时说明本轮修复的模块与范围，以及仍未确认来源时区的历史数据；不得把局部修复表述为全项目已经完成时间改造。
